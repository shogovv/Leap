# Leap 技術メモ(制約とハマりどころ)

実際に踏んだ問題と、その時点で確定した対処。同じ轍を踏まないための記録。

## Manifest V3 / Chrome まわり

- **インライン `<script>` は CSP で禁止**。JS は必ず外部ファイル(`newtab.js` / `i18n.js` / `redirect-focus.js`)に置く。
- **オムニバーが新規タブのフォーカスを奪う**(Chrome 27 以降の仕様)。`redirect-focus.js` が `location.search = "?focus"` へ自己リダイレクトして、オムニバーの「初回ナビゲーション時のフォーカス保護」を回避している。`Esc` でもオムニバーからページへフォーカスを戻せる。
- `chrome.*` API はすべて Promise 形式で `await` する(コールバック形式は使わない)。
- `chrome.search.query({ text, disposition: "CURRENT_TAB" })` でユーザーの既定検索エンジンを使う(`search` 権限)。
- 開いているタブの一覧は「履歴」ではなく「今開いているタブ(`lastAccessed` 降順)」。自分自身(`chrome-extension://<自分>/newtab.html`)と `chrome://` は除外。項目のクリックは `chrome.tabs.update` で切り替え(重複して開かない)。
- 最近閉じたタブは `chrome.sessions.getRecentlyClosed`(Chrome 側の上限 25 件)。復元は `chrome.sessions.restore`(履歴ごと戻る)。
- `chrome://bookmarks/` へのリンクはページ起点だとブロックされるため、`chrome.tabs.create` で開く。

## `location.href = url` は瞬間的ではない

- `location.href` への代入は同期的な**命令**であって、同期的な**遷移**ではない。実際のナビゲーション(DNS 解決・接続など)には実時間の遅延があり、その間ページはまだ生きていて、フォーカス・DOM・イベントリスナーはすべて普通に動く。
- これが原因で起きた実際の不具合:URL 貼り付け時に `preventDefault` + 即座に `location.href` 遷移、という実装にしていたところ、遷移が終わる前にユーザーが習慣で押す次の `Enter` がこのページ自身に届いてしまい、意図しない項目(先頭のブックマーク)を開いてしまっていた。対処は「後から届くかもしれないキー入力に対して安全な状態にする」こと(遷移前に隠し状態を作らない)であって、遅延を減らすことではない。詳細な設計判断は philosophy.md の Enter の節。
- 同種の「confirm してから遅延後に遷移」パターン(`confirmActivate()` の `CONFIRM_DELAY_MS`)にも構造的に同じ危険はある(遅延中に届いた2打目の Enter が、クリアされた入力欄に対して古い描画のままの選択項目を再度開こうとする可能性)。今のところ実害は出ていないが、同種の修正をするときは思い出すこと。
- **副作用(ここでは `clearQueryInput()`)は、実際にそれが要る瞬間まで遅らせる**。`confirmActivate()` と `fireSiteSearch()` はどちらも元々「確認フラッシュ→`CONFIRM_DELAY_MS` 待つ→実際に遷移/切替」という流れの**待つ前**に入力欄を空にしていた。これは「後でこのタブに戻ってきたときに検索欄が空であってほしい」という別の目的(`clearQueryInput()` 自身のコメント参照)のための処理だったが、結果的に「Enter を押した瞬間に入力した文字が一瞬消え、〜160ms 後に実際の遷移が起きる」という、ユーザーには意味不明なちらつきになっていた。直すには、クリア自体は同じでも**実行タイミングを `setTimeout` の外(遅延の前)から中(実際の遷移/切替と同じタイミング)に動かす**だけでよい — 遷移で使う値は先に `const` で確定させておけば、後からクリアしても遷移先には影響しない。

## IME(日本語入力)

- **IME の変換を JS からキャンセルすることはできない**。`blur()/focus()` で無理に切ろうとすると変換中テキストが壊れる(試して却下済み)。
- 正しい対処:`input` イベントの `e.isComposing` が true の間は検索を走らせず、`compositionend` で確定後に検索する。
- **変換確定の Enter が「先頭の結果を開く」を誘発してはいけない**。keydown の Enter で `e.isComposing || e.keyCode === 229` なら何もしない。
- トレードオフ(ユーザー承諾済み):システムの IME が日本語のときに英語入力を強制することはできない。ユーザーが自分で切り替える(英数キーなど)。

## CSS `zoom` の罠

- `body { zoom: 1.1 }` を使っている。`position: fixed` の子孫は、指定した `top/left` が zoom 倍されて描画される。一方 `getBoundingClientRect()` と `window.innerWidth/innerHeight` は実際の(視覚上の)px を返し、ズームされた要素自身の `offsetWidth/offsetHeight` はズーム前のローカル単位。
- ツールチップでは、書き込む座標を zoom で割り、ローカル寸法を viewport と比較するときは zoom を掛けて補正している。
- 新しい固定配置 UI を足すなら、まず `position: sticky`(通常フロー内)で済まないか検討する。sticky は zoom の補正が要らない。

## Chromium の multicol 再描画バグ

- ウィジェット表示(`columns` を使うマソンリー)で、要素の**外側にはみ出す**擬似要素(テープ装飾の `top: -6px`)があると、絞り込みで要素を出し入れしたときに、消えたはずの要素のはみ出し部分が描画ゴミとして残る。
- 対処:テープは `top: 0`(ボックス内)に収める。`.widget::before` と `.folder-row::before` は揃える。

## フォント(Kalam と日本語)

- 検索欄は英字に手書き風の `Kalam` を使うが、Kalam に日本語グリフはない。`.query-input` は `font-family: "Kalam","Zen Maru Gothic",cursive` とし、日本語は Zen Maru Gothic に落とす(汎用 `cursive` のままだと別フォントになる)。
- **行の高さは最初のフォント(Kalam)の字形基準で決まる**。この行の中では日本語グリフが約 1.5px 上に寄って見える。要素ボックスの中心が一致していても、文字の見た目は中心に来ない。
- プレースホルダーは別ブロックなので、日本語のときだけ `html[lang="ja"] ... ::placeholder { font-family: "Zen Maru Gothic" }` で自前の行ボックスにして中心に揃えた。そのため `document.documentElement.lang` を `init()` と `switchLanguage()` で `currentLang` に同期している(`newtab.html` の `lang="ja"` は初期値)。
- 入力欄の `line-height` は `normal` より小さくしても効かない(Chrome の仕様)。
- **中央揃えの確認方法**:要素の `getBoundingClientRect()` 比較では不十分(文字の見た目を見ていない)。ハーネスで `body.style.zoom = 3.5` にし、バーの縦中心に赤い 1px の案内線を `position:absolute` で引いてスクリーンショットを撮り、文字の見た目の中心と比べる。英字は x-height 帯の中心で見る。
- プレースホルダーの色・太さは `getComputedStyle(el, '::placeholder')` で読める。

## サイト内検索(登録ショートカット)

- **チップは検索欄の `Kalam` を継承させない**。以前ハマった「Kalam(英字の手書き風フォント)と日本語グリフの行高メトリクスが違う」問題(下記フォント節)と全く同じ現象が、チップ内の「登録名」と`×`(別フォント指定)の間でも起きた。名前がラテン文字でも日本語でも関係なく再発するため、チップ全体・プレビューパネルの行とも `Zen Maru Gothic` 一本に統一し、色だけで名前を強調する(`Kalam` を混在させない)。
- **テープと同じ `top:0`(はみ出さない)原則を最初から守る**。エンジンのプレビューパネルは `.content` 内に絶対配置で重ねるだけ(マルチカラムの中に置かない)なので multicol 再描画バグの対象にはならないが、念のため擬似要素等でボックス外にはみ出す装飾は増やさない。
- **`getVisibleAnchors()` はサイト内検索が発動中は空配列を返す**。発動中も裏の grid/list はそのまま描画され続ける(暗転させて重ねるだけ)ため、矢印キー/Tab/Ctrl+P・N がこの関数を経由する限り、非表示の選択がパネルの裏で動くのを一箇所で止められる。新しいナビゲーション系のキー操作を足すときも必ずこの関数を経由させること。
- **ネストしたモーダル**は既存の `.modal-backdrop`(z-index:200)の上に `.modal-backdrop.nested`(z-index:300)を重ねる形にした。`Esc` の捕捉フェーズのハンドラは、ネストしたダイアログが開いていればそちらを先に閉じるよう順序を明示している(`isSiteSearchDialogOpen()` を `isModalOpen()` より先に見る)。
- **アイコンは `emoji文字列` か `data:` URL の文字列**として同じフィールド(`icon`)に持たせ、描画側(`renderIconInto()`)で `data:` 判定して `<img>` か `textContent` かを切り替える一本化。アップロード画像は圧縮せず `chrome.storage.local` にそのまま保存するため、200KB のサイズガードを入れている(超えた場合はダイアログ内にインラインエラー、アップロードは反映しない)。

## 配色(ムード)

- 時間帯ムードは `body[data-mood]` で `--paper` / `--ink` / `--card` などの CSS 変数を差し替える仕組み。**文字色に `var(--ink)` を使う要素の背景に固定色(`#fff9e8` 等)を置かない**。夜・深夜は `--ink` が明るい色になるので、クリーム地に薄い文字になって読めなくなる(検索バーで実際に起きた)。背景は `var(--card)` など変数側に揃える。ツールチップは背景・文字とも固定色なので例外。
- 夜系ムードでは `--paper2` と `--card` がほぼ同じ色になる。`--paper2` を「カードより一段沈んだ色」として使う部品(設定モーダルのトグル `.segmented` など)は、夜・深夜だけ個別に上書きしないと選択状態が見分けられない。モーダルの幕(`.modal-backdrop`)も、明色ムード用の茶色の半透明だと暗い紙では背景と同化するので、夜系は黒 `.55` にしている。
- `--sub`(補助文字)は夜 `#bfb39d`、深夜 `#a29580`。以前は深夜で `#7d7161` とコントラストが足りず、11〜12px の小さいラベルが読めなかった。
- 検索バーのプレースホルダーは `--sub` の `opacity:.4` だが、暗い紙では消え入るので night / latenight だけ `.65` にしている。

## パフォーマンス

- 「開いているタブ」は 500 件でも問題ない(`chrome.tabs.query` とプレーンオブジェクトのフィルタは安価)。重いのは DOM 描画。
- そのため `capWhenEmpty` パターン:検索が空のときだけ上位 N 件を描画し、検索中はプール全体に対してマッチしたものだけ描画する。プール自体は切り詰めない。

## ペーストで即遷移(ローカルパスだけ)

- URL は貼り付けただけでは遷移しない(上の「`location.href = url` は瞬間的ではない」参照)。**ローカルファイルパスだけ**は例外として、貼り付けた瞬間に即座に遷移する。理由はURLと違って`chrome.tabs.update()`というブラウザ内部呼び出し一つだけで済み、ネットワーク往復(DNS/TCP/TLS)が発生しないため、反射的な2打目のEnterが割り込める体感できる隙間が実質無いから(詳細は philosophy.md §3)。
- ローカルパスの判定(`isFilePathLike()`)は先頭の形だけ見る(`/`、`<ドライブ文字>:\` or `:/`、`file://`)。`isUrlLike()` と違って**空白を含んでいても弾かない**(実在のファイル名にはスペースが普通に入るため)。両者は先頭が排他的なので誤判定の衝突はない。
- `~/...` はサポートしない。ページ側にホームディレクトリを解決する手段がない(素の HTML/JS でファイルシステムに触れない)ため、`~` はそのまま `file://~/...` のような不正な URL になってしまう。ユーザーには実パスかドラッグ&ドロップ由来のパスを貼ってもらう前提。
- `toFileUrl()` は各セグメントを個別に `encodeURIComponent` してから `/` で繋ぎ直す(スペースや `#` を含むファイル名を通すため)。Windows のドライブ文字(先頭セグメントの `C:`)だけはコロンをエンコードすると壊れるので例外にしている。
- **Chrome 118 以降、拡張機能から `file://` への遷移は既定でブロックされる**。`chrome://extensions` → Leap の詳細 → 「ファイルの URL へのアクセスを許可する」をユーザーが手動で ON にしない限り遷移できない。ユーザー側の一度きりの設定であり拡張機能からは有効化できない。
- そのため `chrome.extension.isAllowedFileSchemeAccess()` を `init()` で一度だけ確認し、`fileSchemeAccessAllowed` にキャッシュしている。ペーストハンドラは、これが `true` のときだけローカルパスのペーストを横取りして遷移する。`false` のとき(既定)は `isFilePathLike()` が true でも何もせず、素の文字列として通常どおり入力欄に貼らせる ── 「横取りしたのに遷移もしない」という一番分かりにくい状態を避けるための分岐。
- **`location.href = "file://..."` は許可を ON にしても遷移しない**(実機の Leap で実際に踏んだ:トグルを ON にした後でも、ペーストで `preventDefault` だけ効いて入力欄にも何も残らず、遷移もしない)。「ファイルの URL へのアクセスを許可する」トグルが実際にゲートしているのは `chrome.tabs.update()` / `chrome.windows.create()` などタブ操作 API 経由の遷移で、ページ自身の `location.href` 直接遷移(ページ read-navigation)は別の仕組みでブロックされたままになる。**ローカルパスへの遷移は `chrome.tabs.update({ url })` を使うこと**(`location.href` ではなく)。

## 検索ロジック

- 空白区切りのトークンはすべて満たす必要がある(AND)。各トークンは、ラベル・URL・**フォルダ名**のいずれかに含まれていればよい。フォルダ名だけ打てば中身が全部出る。

## ツールチップ

- ネイティブの `title=` は表示まで 1〜1.5 秒かかり遅い。`data-tooltip` + JS(`TOOLTIP_DELAY_MS = 250`)の独自ツールチップを `document` レベルで委譲して使う。ヘッダーのボタンも同じ仕組み。

## i18n の構造

- `MESSAGES = { ja: {...}, en: {...} }` を `t(key)` で引く(ja へフォールバック)。
- `MOODS[mood].greetings = { ja: [100], en: [100] }`、`PLACEHOLDERS` と `EMPTY_STATES` は `{ ja: [10], en: [10] }`。`emptyHint` は `{query}` を置換する文言。空状態の1行目は `renderEmptyState()` が「0件になった時点」で一度だけ選び、0件が続く間は固定する(毎キー入力で選び直すとちらつく)。DOM は `textContent` で組み立て、入力文字を `innerHTML` に入れない。
- 疑似セクションは `name` ではなく `nameKey` を持ち、描画時に `t()` で解決する。
- 設定は `chrome.storage.local` に `{ moodMode, view, lang }`。`init()` の最初に読み込んでから描画する。
- サイト内検索の登録一覧は別キー `siteSearches`(`{id,name,keyword,url,icon,color}[]`)。同じく `init()` で読み込む。保存は `saveSettings()` とは別の `saveSiteSearches()`。
- `HELP_ROWS` の3番目の要素(mode)は `"plain"`(実在するキーがない行 — バッジ化しない)か省略時の既定 `"badges"`。`badges` モードの `i18n.js` 側の値は簡易DSL:`|` で複数キーに分割(それぞれ独立した `.kbd` バッジ)、`::` の後ろは地の文の補足(バッジ化しない)。この2文字("|"、"::")は翻訳文言の中では区切り文字として予約されているので、キー表記そのものに使わない(今のところ衝突なし)。

## `<details>`/`<summary>` の折りたたみ確認方法

- AIサポートのブロックは `<details>` で折りたたんでいる(JS状態管理なし)。**折りたたみの確認を `getComputedStyle().display` や `offsetParent`、`getBoundingClientRect()` でやると「非表示になっていない」ように見えて誤検知する** — Chromium はこの折りたたみを子要素自身の `display` を変えずに(内部の `::details-content` 相当の層で)実現しているため、子要素側からは畳まれているかどうか分からない。
- 正しい確認方法は Playwright の `locator.isVisible()`(実際の可視性アルゴリズムを使う)か、素直にスクリーンショットで目視すること。
